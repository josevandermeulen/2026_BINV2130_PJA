Lire un fichier texte

Pour lire le contenu d'un fichier texte ligne par ligne, Java propose la classe BufferedReader, qu'on construit généralement à partir d'un FileReader.

FileReader + BufferedReader

FileReader(String chemin) BufferedReader(Reader reader) String readLine() 
FileReader fileReader = new FileReader("logs/index.txt");
BufferedReader reader = new BufferedReader(fileReader);

String ligne = reader.readLine();
while (ligne != null) {
    System.out.println(ligne);
    ligne = reader.readLine();
}

reader.close();

FileReader ouvre le fichier ; BufferedReader l'enveloppe (un décorateur) pour offrir la méthode readLine(), qui lit une ligne complète et renvoie null lorsqu'il n'y a plus rien à lire.

Le chemin passé au constructeur (par exemple "logs/index.txt") est relatif au répertoire de travail du programme — dans IntelliJ, il s'agit par défaut de la racine du projet. Placer les fichiers de données à la racine du projet, pas dans un sous-dossier de packages ni dans src/.

Forme condensée de la boucle de lecture

String ligne;
while ((ligne = reader.readLine()) != null) {
    System.out.println(ligne);
}

L'affectation ligne = reader.readLine() a pour valeur la ligne lue ; la boucle continue tant que cette valeur n'est pas null. C'est la forme la plus courante en pratique.

Exceptions vérifiées et E/S

Contrairement à IllegalArgumentException (une exception non vérifiée, que le compilateur ne vous oblige pas à traiter), les opérations d'entrée/sortie peuvent lever IOException, qui est une exception vérifiée (checked exception).

Deux façons de traiter une exception vérifiée

  1. L'attraper avec un try/catch.
  2. La propager avec throws IOException sur la méthode.
// Propagation : la méthode appelante devra elle-même traiter IOException
public void afficherFichier(String chemin) throws IOException {
    BufferedReader reader = new BufferedReader(new FileReader(chemin));
    // ...
}
Une méthode qui ouvre un fichier peut échouer pour de nombreuses raisons indépendantes du code (fichier absent, droits insuffisants, disque plein...). Le compilateur force donc à décider explicitement quoi faire dans ces cas, contrairement aux exceptions non vérifiées.

Hiérarchie utile

Exception Vérifiée ? Cause typique
IOException Oui Erreur générale d'entrée/sortie (disque, permissions...).
FileNotFoundException Oui (sous-classe d'IOException) Le fichier demandé n'existe pas à l'ouverture.
IllegalArgumentException Non Donnée invalide (pas liée à l'E/S elle-même).

try-with-resources

La lecture « manuelle » vue plus haut a un défaut : si une exception survient entre l'ouverture et le reader.close(), le fichier ne sera jamais fermé. Sur un programme qui tourne longtemps, cela finit par épuiser les descripteurs de fichiers disponibles.

Syntaxe

try (BufferedReader reader = new BufferedReader(new FileReader("logs/index.txt"))) {
    String ligne;
    while ((ligne = reader.readLine()) != null) {
        System.out.println(ligne);
    }
}

Ici, reader.close() est appelé automatiquement, même si readLine() lève une exception au milieu de la boucle. C'est équivalent à un try { ... } finally { if (reader != null) reader.close(); } écrit à la main, mais plus lisible et moins sujet à l'oubli.

Plusieurs ressources

try (BufferedReader reader = new BufferedReader(new FileReader("logs/index.txt"));
     BufferedWriter writer = new BufferedWriter(new FileWriter("rapport.txt"))) {
    // ...
}

On peut déclarer plusieurs ressources séparées par ; ; elles sont fermées automatiquement dans l'ordre inverse de leur déclaration.

Introduit en Java 7, le try-with-resources est la façon idiomatique d'ouvrir une ressource fermable en Java moderne. En dehors d'un cas d'apprentissage explicite, préférer systématiquement cette forme à un close() manuel.

AutoCloseable

Une classe peut être utilisée dans un try-with-resources si elle implémente l'interface AutoCloseable (une seule méthode abstraite : close()).

Signature

public interface AutoCloseable {
    void close() throws Exception;
}

BufferedReader, BufferedWriter, FileReader et FileWriter implémentent tous AutoCloseable (via Closeable), ce qui explique qu'on peut les utiliser directement après try.

Écrire un fichier texte

L'écriture fonctionne de manière symétrique à la lecture, avec FileWriter et BufferedWriter.

FileWriter + BufferedWriter

FileWriter(String chemin) FileWriter(String chemin, boolean append) void write(String texte) void newLine() 
try (BufferedWriter writer = new BufferedWriter(new FileWriter("rapport.txt"))) {
    writer.write("Bonjour");
    writer.newLine();
}
Par défaut, new FileWriter(chemin) écrase le fichier existant. Pour ajouter à la suite d'un fichier existant plutôt que l'écraser, utiliser le constructeur à deux arguments : new FileWriter(chemin, true).

Écrire plusieurs lignes

List<String> ipsUniques = List.of("10.0.0.1", "10.0.0.2", "10.0.0.5");

try (BufferedWriter redacteur = new BufferedWriter(new FileWriter("rapport.txt"))) {
    for (String ip : ipsUniques) {
        redacteur.write(ip);
        redacteur.newLine();
    }
    redacteur.write("Nombre d'adresses IP uniques : " + ipsUniques.size());
    redacteur.newLine();
}

Stream<String> depuis un fichier

BufferedReader fournit une méthode lines() qui renvoie directement un Stream<String>, une ligne par élément — pratique pour enchaîner l'API Stream sur le contenu d'un fichier sans écrire soi-même la boucle readLine().

lines()

Stream<String> lines() 
try (BufferedReader lecteur = new BufferedReader(new FileReader(chemin))) {
    List<String> lignes = lecteur.lines().collect(Collectors.toList());
}
Le Stream renvoyé par lines() reste lié au BufferedReader sous-jacent : il doit être consommé (par exemple avec collect) avant la fermeture du reader à la sortie du bloc try-with-resources. Ne pas renvoyer ce Stream tel quel en dehors du bloc.

java.nio.file.Files

Le package java.nio.file (Java 7+) fournit une API plus moderne pour manipuler des chemins et des fichiers, en complément des classes historiques de java.io. Un Path représente un chemin ; la classe utilitaire Files regroupe des opérations statiques sur les fichiers qu'il désigne.

Construire un chemin

static Path of(String first, String... more) 
Path racine = Path.of("logs-grand-volume");
Path fichier = racine.resolve("2026-01-01.log"); // combine deux segments de chemin

Vérifier et créer

static boolean exists(Path path) static Path createDirectories(Path dir) 
if (!Files.exists(Path.of("logs-grand-volume"))) {
    Files.createDirectories(Path.of("logs-grand-volume"));
}

createDirectories crée aussi, si nécessaire, tous les répertoires parents manquants (contrairement à createDirectory, qui échoue si le parent n'existe pas).

Lire tout le contenu en une fois

static List<String> readAllLines(Path path) 
List<String> lignes = Files.readAllLines(Path.of("rapport.txt"));

Pratique pour un test ou un petit fichier : contrairement à BufferedReader, aucune gestion manuelle de ressource n'est nécessaire, readAllLines ouvre et ferme le fichier elle-même. Pour un très gros fichier, préférer une lecture ligne par ligne (BufferedReader ou Files.lines(Path), qui renvoie un Stream<String> paresseux) afin de ne pas tout charger en mémoire d'un coup.

Convertir vers l'API historique si besoin

Path chemin = racine.resolve("index.txt");
BufferedWriter writer = new BufferedWriter(new FileWriter(chemin.toFile()));

Path.toFile() convertit vers l'ancien type java.io.File, utile quand une API plus ancienne (comme le constructeur de FileWriter) attend un File plutôt qu'un Path.

Validation vs erreurs techniques

Une ligne d'un fichier peut être syntaxiquement lisible (readLine() réussit) mais représenter des données invalides (un champ manquant, un nom vide...). Ce n'est pas une IOException : c'est une erreur de validation, qui remonte typiquement sous forme d'IllegalArgumentException.

Ne pas interrompre tout le traitement pour une ligne invalide

try {
    acces.add(parserLigne(ligne));
} catch (IllegalArgumentException e) {
    System.out.println("Ligne ignorée : " + ligne);
}

Ces exceptions ne sont pas vérifiées : rien n'oblige à les traiter, mais on choisit ici de les attraper pour ignorer la ligne fautive sans interrompre tout le programme.

Un fichier référencé mais absent

Un fichier mentionné dans un index mais absent du disque lève une FileNotFoundException (une sous-classe d'IOException, donc vérifiée). Si l'on veut que le chargement continue avec les fichiers suivants, on attrape spécifiquement cette exception-là — les autres IOException, elles, continuent de se propager.

for (String nomFichier : lecteur.lireIndex(dossier + "/index.txt")) {
    try {
        acces.addAll(parserLignes(lecteur.lireLignes(dossier + "/" + nomFichier)));
    } catch (FileNotFoundException e) {
        System.out.println("Fichier introuvable : " + nomFichier);
    }
}
Ne jamais mélanger validation métier et gestion d'erreurs techniques dans le même catch : une IOException (problème d'accès au fichier) et une IllegalArgumentException (problème de contenu) appellent des réactions différentes et ne doivent pas être traitées comme un seul et même cas d'erreur générique.

Exemple complet

Un scénario typique : un dossier logs/ contient un fichier d'index (index.txt, un nom de fichier de logs par ligne) et plusieurs fichiers de logs à charger, parser puis analyser.

Lire l'index et un fichier de logs

public List<String> lireIndex(String chemin) throws IOException {
    List<String> noms = new ArrayList<>();
    try (BufferedReader lecteur = new BufferedReader(new FileReader(chemin))) {
        String ligne;
        while ((ligne = lecteur.readLine()) != null) {
            noms.add(ligne);
        }
    }
    return noms;
}

public List<String> lireLignes(String chemin) throws IOException {
    try (BufferedReader lecteur = new BufferedReader(new FileReader(chemin))) {
        return lecteur.lines().collect(Collectors.toList());
    }
}

Combiner index, parsing et résilience aux erreurs

public List<Acces> chargerTousLesAcces(String dossier) throws IOException {
    List<Acces> acces = new ArrayList<>();
    for (String nomFichier : lireIndex(dossier + "/index.txt")) {
        try {
            acces.addAll(parserLignes(lireLignes(dossier + "/" + nomFichier)));
        } catch (FileNotFoundException e) {
            System.out.println("Fichier introuvable : " + nomFichier);
        }
    }
    return acces;
}

public List<Acces> parserLignes(List<String> lignes) {
    List<Acces> acces = new ArrayList<>();
    for (String ligne : lignes) {
        try {
            acces.add(parserLigne(ligne));
        } catch (IllegalArgumentException e) {
            System.out.println("Ligne ignorée : " + ligne);
        }
    }
    return acces;
}

Écrire un rapport à partir de résultats calculés par Stream

public void ecrireRapport(String chemin, List<Acces> acces) throws IOException {
    List<String> ips = acces.stream()
        .map(Acces::getIp)
        .distinct()
        .sorted()
        .toList();

    try (BufferedWriter redacteur = new BufferedWriter(new FileWriter(chemin))) {
        for (String ip : ips) {
            redacteur.write(ip);
            redacteur.newLine();
        }
        redacteur.write("Nombre d'adresses IP uniques : " + ips.size());
        redacteur.newLine();
    }
}

Rappels du langage (séance 2)

La séance 2 revient sur six points du langage, sur la pizzeria de la séance 1.

Un énuméré est une classe

public enum Categorie {

    VEGETARIENNE("végétarienne"),

    VIANDE("viande");

    private final String libelle;

    Categorie(String libelle) {        // toujours privé
        this.libelle = libelle;
    }

    public String getLibelle() {
        return libelle;
    }

    public boolean estViande() {
        return this == VIANDE;         // une constante se compare avec ==
    }

}

Categorie.VIANDE.getLibelle();         // "viande"

Chaque constante est un objet, créé une seule fois par le constructeur avec les arguments écrits entre parenthèses.

Une Map dont la valeur est une collection

V computeIfAbsent(K cle, Function<K, V> creation) 
Map<Categorie, SortedSet<Pizza>> carte = new HashMap<>();

// ajout : l'ensemble est créé au premier ajout dans la catégorie
carte.computeIfAbsent(pizza.getCategorie(), c -> new TreeSet<>()).add(pizza);

// retrait : la clé disparaît avec le dernier élément
SortedSet<Pizza> ensemble = carte.get(pizza.getCategorie());
ensemble.remove(pizza);
if (ensemble.isEmpty()) {
    carte.remove(pizza.getCategorie());
}

Comparable et Comparator

int compareTo(T autre) // Comparable : l'ordre naturel, un seul int compare(T o1, T o2) // Comparator : un ordre extérieur, autant qu'on veut 
// classe nommée
menu.sort(new ComparateurPrix());

// classe anonyme
menu.sort(new Comparator<Pizza>() {
    @Override
    public int compare(Pizza p1, Pizza p2) {
        return Double.compare(p1.calculerPrix(), p2.calculerPrix());
    }
});

// lambda
menu.sort((p1, p2) -> Double.compare(p1.calculerPrix(), p2.calculerPrix()));

Résultat négatif : le premier se place avant ; nul : même rang ; positif : après. Comparez avec Integer.compare / Double.compare, jamais par soustraction.

Varargs

public int ajouter(Ingredient... ingredients) {   // un tableau Ingredient[] dans la méthode
    int nombre = 0;
    for (Ingredient ingredient : ingredients) {
        if (ajouter(ingredient)) {
            nombre++;
        }
    }
    return nombre;
}

pizza.ajouter(Ingredients.TOMATE, Ingredients.THON);   // de zéro à n arguments, ou un tableau

Le varargs est toujours le dernier paramètre. Avec un seul argument, une surcharge à paramètre unique est préférée au varargs.

Type de retour covariant

public abstract class Pizza {
    public abstract Pizza copier();
}

public class PizzaComposee extends Pizza {
    @Override
    public PizzaComposee copier() {   // sous-type de Pizza : accepté
        // ...
    }
}

Une redéfinition peut restreindre son type de retour à un sous-type, jamais l'élargir ; les paramètres restent identiques.

Classes internes

public class Pizzeria {

    private Set<Commande> commandes = new LinkedHashSet<>();

    public static class Bilan { ... }        // liée à aucune Pizzeria : new Pizzeria.Bilan(...)

    public class Fidelite {                  // liée à la Pizzeria qui l'a créée
        public boolean aDesCommandes() {
            return !commandes.isEmpty();     // Pizzeria.this.commandes
        }
    }

}
À retenir : déclarez une classe interne static sauf si elle a besoin des attributs de l'objet englobant.

Pièges fréquents

Problème Cause probable Correction
Erreur de compilation : « unreported exception IOException; must be caught or declared to be thrown ». Une opération d'E/S vérifiée n'est ni attrapée ni propagée par la méthode qui l'appelle. Ajouter throws IOException sur la méthode, ou l'entourer d'un try/catch.
FileNotFoundException alors que le fichier existe pourtant. Le chemin est relatif à un répertoire de travail différent de celui attendu (souvent : fichier placé dans un package au lieu de la racine du projet). Vérifier le répertoire de travail (racine du projet dans IntelliJ) et y placer les fichiers de données, hors de src/.
Le fichier écrit est vide ou tronqué, malgré des appels à write(...). Le BufferedWriter n'a pas été fermé : les données restent dans le tampon interne et ne sont jamais réellement écrites sur le disque. Utiliser systématiquement un try-with-resources, qui garantit l'appel à close() (donc le vidage du tampon) même en cas d'exception.
Le fichier de sortie ne contient que la dernière exécution, les précédentes ont disparu. new FileWriter(chemin) écrase le fichier existant par défaut. Utiliser new FileWriter(chemin, true) pour ajouter à la suite du contenu existant.
UncheckedIOException (IOException: Stream closed) en essayant de réutiliser le Stream<String> renvoyé par lines() après le bloc try-with-resources. Le BufferedReader sous-jacent a déjà été fermé à la sortie du bloc, or lines() est paresseux et lit depuis ce reader à la demande. Consommer le stream (collect, toList...) à l'intérieur du bloc try-with-resources, avant la fermeture.
Une seule ligne mal formée fait planter tout le chargement du fichier. L'exception de validation (IllegalArgumentException) n'est pas attrapée ligne par ligne, elle remonte et interrompt toute la boucle. Entourer le parsing de chaque ligne d'un try/catch (IllegalArgumentException e) pour ignorer uniquement la ligne fautive.
Un seul fichier manquant dans l'index fait planter tout le chargement. FileNotFoundException non attrapée spécifiquement lors du chargement d'un fichier référencé par l'index. Attraper FileNotFoundException autour de la lecture de chaque fichier de l'index, en laissant les autres IOException se propager.
